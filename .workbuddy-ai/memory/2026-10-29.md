# 2026-10-29

## 新增：多 PDF 合并（缩略图拖拽排序）

用户需求：「开发一个合并功能，可以将不同的 PDF 进行合并，鼠标拖拽排序，
windows 和 uos 都一起」。

### 设计

**页序只有一份真相**：`MergePlan.order`，每项是 `(源文件下标, 源文件内页码)`。

- 拖拽、删页都只改这张表，源文件一个字节不动 → 反复调整不累积质量损失，
  也不需要给合并单独做撤销栈
- 写文件时才按顺序 `insert_pdf`，并把连续页压成区间
  （`_runs()`）：300 页合并 1.8 秒，不压区间就是 300 次调用
- 源文件列表只管「有哪些文件」，顺序在预览里拖；两套顺序会打架，所以只留一套

**两级结构**：`core/merge.py`（无 Qt）+ `ui/merge_dialog.py`。

### 几个非显而易见的坑

1. **`QAbstractItemView::dropEvent` 对 InternalMove 有硬性检查**：
   `event->source() != this` 就直接 return。而 `source()` 只能由
   `QDrag::exec()` 设置，**测试里造不出来**（QDropEvent 构造函数没有 source 参数）。
   所以真实内部拖拽无法自动化测试。
   → 把「Qt 搬完行之后做什么」抽成 `after_drop()`，测试直接调它，
     测的是真实代码路径而不是在测试里复刻逻辑。

2. **`QListWidgetItem` 移动时图标跟着 item 走**，所以「拖完检查图标对不对」
   在缩略图已渲染完的情况下永远通过 —— 假绿。
   要抓到串页，必须**在还有未渲染页的时候拖**（`assert lst._pending` 守住这个前提）。

3. **`self._key_rows = {}` 在文件里出现 3 次**，用 `str.replace(..., 1)` 破坏代码
   验证测试时打中了错误的那个，白验证一轮。破坏性验证必须用唯一上下文
   （带上后面的 `if key is None:`）并 assert 命中。

4. **白色页面在 `#f3f4f7` 画布上看不出边界**。截图里看起来像「缩略图被压扁成
   55×42」，实测 `visualItemRect` 是 114×169、icon pixmap 是 100×141，全对。
   是纯视觉问题 → 给 `render_page_pixmap` 加 `border` 参数描一圈细线。

5. **`gridSize` 里已经含了间距**，再 `setSpacing(4)` 会白吃掉一列
   （847px 宽只能放 6 个而不是 7 个）。

### 测试

- `smoke_core.py` 27 → **38 项**：页序、删页、移除源文件（下标前移）、
  加密源、损坏文件、空计划、页序校验、覆盖输出、自然排序、区间压缩
- `ui_smoke.py` 16 → **23 项**：添加、拖拽后模型/编号/缩略图三方一致、
  删页、移除源文件重挂、外部拖入、拖拽后写出文件页序正确、空状态
- `_audit_thumbs.py` 25 场景不变

**有效性验证**：去掉 `renumber` 里的 `self._key_rows[key] = row` + 行号守卫后，
「拖拽排序」「移除源文件」两项都变红（`第 1 格（(0, 1)）显示的页不对`）。

### 性能

- 300 页添加 113ms、首次布局 48ms、缩略图 1 秒 84 张（可见区优先）
- 300 页合并写出 1792ms，输出 1.2MB
- `_cache` 上限 500 张 pixmap（100×141×4 ≈ 56KB，约 28MB）

### 兼容性

- Python 3.7 / PyQt5：AST 检查无 3.8+ 语法（walrus / f-string）
- 无 `winreg` / `os.startfile` / `ctypes` 等平台专属调用
- 文件名自然排序用 `re.split(r"(\d+)")`，`file2` 排在 `file10` 前
- 中文文件名按 Unicode 码点排序（不是拼音），与 Windows 资源管理器不同，
  但分卷文件的数字顺序是对的
