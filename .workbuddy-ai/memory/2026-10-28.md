## UOS apt 源封闭 → 改走离线 wheel

用户反馈安装脚本卡在「pip 安装 PyQt5（约 60MB，请耐心等待）」，并指出
**UOS 的 apt 是封闭的**。查证确认：

- UOS 默认源是 `professional-packages.chinauos.com/desktop-professional`，
  **必须系统已激活**才能拉包，未激活时 `apt install python3-pyqt5` 直接失败；
- 另外 UOS 没开**开发者模式**时，sudo 装包会被安全策略拦
  （标记文件 `/etc/uos-developer-mode` 或 `/var/lib/deepin/developer_mode`）；
- `python3-pip` 本身也要 apt 装 → 源不通时形成死循环。

所以 apt 这条路在 UOS 上根本靠不住，改成三级降级：

1. **本地 wheel 目录**（新增，最优先）：`packaging/wheels/*.whl` → `pip install --no-index --find-links`
2. **pip + 清华镜像**：`--timeout 60 --retries 3 -i <镜像>`
3. **venv 兜底**

### 新增 `packaging/fetch_wheels.sh`

在任意有网机器（Windows 也能跑）上把 Linux wheel 下好，拷到 UOS 离线装。
关键参数（**不要传 `--abi`**）：

```
pip download --only-binary=:all: --platform manylinux2014_x86_64 \
    --python-version 37 --implementation cp -d wheels PyQt5 pymupdf
```

传 `--abi cp37m` 会漏掉 abi3 的 PyQt5，只能拿到 5.15.7 之前的版本。

Python 3.7 实测可用组合（共 80MB）：
`PyQt5-5.15.7-cp37-abi3-manylinux1` + `PyQt5_sip-12.12.2-cp37` +
`pyqt5_qt5-5.15.19-py3-none-manylinux2014` + `PyMuPDF-1.22.5-cp37-cp37m-manylinux2014`

`make_release.sh --with-wheels` 可把 wheels 一起打进发行包（79MB），
拷过去解压即装，全程不需要网络。

## 新增面向新手的 `安装说明.md`

用户装成功后要求写一份「Linux 小白也能照着做」的安装说明。
单独成文（`安装说明.md`），README 里加了一句话入口，两份文档分工：
README 偏开发与排错，安装说明只讲操作。

写这类文档的几条原则（这次验证有效）：

- 每步先讲**在哪做**（哪个窗口、哪个目录），再给命令，最后讲**看到什么算成功**
- 小白最常卡的三处必须写：终端粘贴是 `Ctrl+Shift+V`（不是 `Ctrl+V`）、
  sudo 输密码时**屏幕上什么都不显示**、`cd` 的路径怎么用 `Ctrl+L` 拿到
- 优先给「文件管理器里右键 → 在终端中打开」这种免 `cd` 的路径
- 错误对照表按「你看到什么 → 为什么 → 怎么办」三列，比讲原理有用
- 别写原理，别写 wheels 是什么，只说「这个文件夹别删」

踩到的细节：`--user` 模式**也会**写 desktop 文件到
`~/.local/share/applications`，启动器里能搜到，只是终端要敲
`~/.local/bin/pdfstudio`。一开始写成了「不会出现在启动器里」，是错的。

## 修 bug：插入页面后缩略图被压扁、点不中

用户截图反馈：右键「在此页之后插入空白页」之后，左侧导航的缩略图
缩成一条细线，完全没法选。

**根因**：`ThumbnailList.refresh_all()` 给新增条目 `addItem` 时**没有 `setIcon`**
（`set_document()` 里有，`refresh_all()` 里漏了）。空图标的 item sizeHint
只有几十像素，而列表开了 `setUniformItemSizes(True)`，Qt 用这个极小的
sizeHint 当统一尺寸，于是**整列缩略图一起被压扁**。复现数据：
插入前 124×187，插入后 52×18。

**修复**（`pdfstudio/ui/side_panel.py`）：
1. `refresh_all()` 里新增 item 时也挂 placeholder 图标
2. 结束时调一次 `doItemsLayout()` 强制重排，否则旧格子尺寸会沿用

### 这次的教训

14. **异步渲染会掩盖状态 bug**。`_render_next` 12ms 一页，很快就把图标补上了，
    所以「检查 icon 是否为空」的断言抓不住——bug 在于**布局已经被污染**，
    补了图标也不会恢复。必须测 `visualItemRect()` 的实际矩形。
15. **`visualItemRect()` 对滚动区外的 item 返回 0×0**，断言会误报。
    要测**一定可见的** `item(0)`，而不是刚插入的最后一页。
16. **侧栏刷新有 350ms 防抖**（`_panel_timer`），测试里 `pump` 少于这个值
    会拿到 `item(n) is None`。
17. 验证测试有效性的标准做法：**把修复注释掉，确认测试变红**。
    这次第一版断言（查 icon 非空）在回退后仍然通过，说明它没用，必须重写。

## 缩略图专项审计（用户：删页之后缩略图也有问题，你都一起测试一下）

用户明确指出上一条是"我说一下你改一下"的被动修补，要求**一次性**排查

### 新增 `tests/_audit_thumbs.py`（23 个场景，全绿）

初始 → 首页后插 → 末页后插 → 中间插 → 快速连插 3 页 → 从文件插多页 →
删中间 → 删首页 → 删末页 → 删多页 → 删开头连续两页 → 旋转 → 下移 →
上移 → 移到末尾 → 移到开头 → 撤销到底 → 重做到底 → 删到只剩一页 →
只剩一页再插 → 关闭文档 → 大文档可见区优先 → 滚动后可见区优先。

每个场景查 5 类不变量：条目数 vs 页数、UserRole、条目文字、格子矩形高度、
**缩略图画的是不是这一页**，外加当前行 vs 视图页。

### 关键：布局对了 ≠ 画对了

只查条目数和尺寸抓不住"删页后缩略图还是旧页"。新增内容校验：
把缩略图缩成 **4×4 颜色指纹**，和按同样参数（`THUMB_WIDTH` 缩放）直接
渲染出来的页面逐格比，色差 > 34 判错。

- 造样本必须**每页颜色明显不同**（顶部刷一条独占色带）。
  `samples/sample.pdf` 每页都是白底黑字，粗粒度指纹分不出来，
  故意把 `refresh_all` 的 `_pending` 清空制造"不重绘"，测试照样全绿。
- 一开始我按"索引 → 调色板"推算期望色，错得离谱：插入空白页后第 1 页
  本来就该是白的，旋转后色带也换位置。**期望值必须从当前文档实际渲染结果
  取**，不能按索引猜。

### 顺手改掉的体验问题

`_render_next` 原来按顺序一页一页画，200 页文档要画 11 秒，滚到后面
一片灰块。改成 `_pick_next()` **可见区优先**，`_pending` 按离当前页的距离
排序。实测：200 页文档打开 400ms 内可见 6 张全部就绪；滚到第 150 页
400ms 内 4/4 就绪。渲染本身只要 1.6ms/张，瓶颈是 12ms 定时器间隔。

### 测试工程化

- 抽出 `tests/_thumb_probe.py`：`grid_signature` / `page_signature` /
  `mismatch` / `make_color_pdf` / `pump` / `settle`，审计和正式测试共用。
- `settle()` 必须**等渲染队列清空**（盯 `th._pending` 和 `th._timer`），

- `ui_smoke.py` 新增第 15 项「增删页面后缩略图与文档一致」，

- **两项都做了回退验证**：去掉 placeholder 图标 → `t_page_ops` 报

### 新教训

18. **"删页导致缩略图异常"和"插页导致压扁"不是同一个 bug**。删除只减少
    条目，不会触发 `uniformItemSizes` 压扁；删除的风险是**内容不重绘**。

19. 回归测试里"等渲染完成再断言"会**掩盖压扁 bug**——图补齐后 Qt 自己

    的窗口期量。
20. 用户要求"一起测试"时，正确做法是**写穷举脚本**而不是逐个手动试；
    脚本本身就是交付物，能反复跑。

## 发行包"变小了"的乌龙（用户：压缩包怎么只有 600k 了）

**现象**：用户发现 `pdfstudio-1.0.0.tar.gz` 从 79MB 变成 363K。

**原因**：修完缩略图后重新打包时只跑了 `bash packaging/make_release.sh`，
**漏了 `--with-wheels`**。这个脚本默认排除 `packaging/wheels/`（80MB），
打出来的是纯源码包。而 UOS 的 apt 源是封闭的，离线 wheel 恰恰是能装上的
唯一保障——包变小 = 装不上。

**修复**：
1. 重打 `--with-wheels` → 79MB / 64 个条目，4 个 wheel 齐全
   （PyQt5 5.15.7 cp37-abi3、pyqt5_qt5 5.15.19、PyQt5_sip、PyMuPDF 1.22.5，
   都是 manylinux2014 x86_64，对应 UOS 20 的 Python 3.7）
2. 解包复验：`tests/smoke_core.py` 26 项通过，wheel 目录 80M 完整
3. `make_release.sh` 加防护：`wheels/` 存在但没加 `--with-wheels` 时
   打印三条 `!!` 警告，说明纯源码包在 UOS 上多半装不上

**教训 21**：交付物"体积"本身就是契约的一部分。79MB 是带离线依赖、
363K 是纯源码，两者用途完全不同。重新打包前先确认 `ls -lh packaging/build/`，
**给 UOS 用户的包必须是 79MB 那个**。

## 真正的根因：缩略图按宽度缩放，长条页撑爆格子

用户补充说明：「删除后的略缩图间隔变大，然后上下都缺内容了」。
之前两轮都在查"重绘/布局"，方向偏了——这是**渲染尺寸**问题。

### 根因

`_render_next` 里：

```python
zoom = THUMB_WIDTH / float(page.rect.width or 595)   # 只按宽度算
```

图标高度 = `THUMB_WIDTH * 页面高/宽`，**页面比例一变就变**。
而格子 `gridSize` 是固定的 `THUMB_WIDTH+26 × THUMB_WIDTH*1.414+34`（144×201）。
公文里混着长条页、横向表格页时：

- 长条页（595×1150）→ 图标 118×238，被塞进 196 高的格子 → **上下各裁掉约 21px**
- 横向页（842×595）→ 图标 118×84 → 上下留大片空白
- 同一份文档里图标高度实测出现过 **84 / 167 / 168 / 195 / 238 五种**

于是"间隔忽大忽小"+"缩略图上下缺内容"同时出现。用户截图里第 2 页正是被裁的那张。

### 修复（`pdfstudio/ui/side_panel.py`）

抽出 `render_page_pixmap(page)`：`scale = min(THUMB_WIDTH/w, THUMB_HEIGHT/h)`，
把页面画到**固定 118×167 画布**上居中，比例不符的地方留白（#f3f4f7）。
新增常量 `THUMB_HEIGHT = 167`，`iconSize` 和 `gridSize` 都从它推导。

**关键**：`tests/_thumb_probe.page_signature()` 改为直接调用
`render_page_pixmap()`，不再自己写一遍缩放公式——两边公式一旦分叉，
校验就会误报或漏报。

### 新增回归

- `_thumb_probe.make_mixed_pdf()`：A4 / 长条 / 横向 / 小页混排的 10 页素材
- `_audit_thumbs.py` 新增 2 个场景「混合页面尺寸」「混合尺寸删页后」
- `ui_smoke.py` 第 16 项「页面尺寸混杂时格子保持一致」
- 回退验证：把 `min(...)` 改回 `THUMB_WIDTH / width` → 审计报
  `图标尺寸不统一 [(118,84),(118,167),(118,168),(118,195),(118,238)]`，
  ui_smoke 报同样的错。**有牙齿**。

### 教训

22. 用户说"缩略图有问题"，可能是**渲染尺寸**、**重绘时机**、**布局格子**
    三件完全不同的事。前两轮只查了后两件，白跑两趟。看到"间隔变大 +
    上下缺内容"这种描述，应该立刻想到"图比格子大，被裁了"。
23. 缩略图这类"固定格子"控件，图标必须画到**固定尺寸画布**上，
    绝不能按内容比例算。只要允许图标尺寸浮动，`setUniformItemSizes`
    和 `setGridSize` 就会打架。
24. 校验代码不要重复实现被测逻辑的公式——让它调用被测代码本身，
    否则修了 A 忘了改 B，测试会一直绿。

## Windows 版打包（用户：自己+同事用，要关联 PDF，目标机器没 Python）

评估结论：代码 5619 行零平台分支，整套测试本来就跑在 Windows 上，
所以不是"移植"而是"打包"。实际做下来印证了这一点——**没改一行界面代码**。

### 做了什么

1. `run.py` 加 `--selftest <png>`：真建窗口、开 PDF、截图、再用 QPrinter
   输出一份 PDF 验证打印链路。打包后没法人工点，只能靠它。
2. `packaging/windows/pdfstudio.spec`：PyInstaller 单目录模式
3. `packaging/windows/app.ico`：从 256px PNG 转的多尺寸 ico
4. `install.ps1` / `uninstall.ps1` / `安装.bat` / `卸载.bat`：
   **按用户安装到 %LOCALAPPDATA%，不需要管理员权限**
5. `make_zip.py` → 51MB 分发包；`clean.py` 清中间产物
6. `使用说明.txt`：给最终用户

### 踩到的坑（都写进代码注释了）

- **`QtPrintSupport` 必须显式写进 hiddenimports**。Qt6 把打印插件并进了
  `Qt6PrintSupport.dll`，没有独立的 printsupport 插件目录，所以"看插件在不在"
  这种检查会误判。自检里直接跑一遍 QPrinter 才靠得住。
- **体积**：160MB → 122MB。砍掉 `opengl32sw.dll`（20MB，纯控件不走 GL）、
  PIL（11MB，只有测试用）、非中文翻译（6MB）。不开 UPX，UPX 是杀软误报重灾区。
- **`.ps1` 必须带 UTF-8 BOM**，否则 PS 5.1 按 ANSI 解析，中文全乱码；
  **`.bat` 必须没有 BOM**，否则 cmd 把 BOM 当命令执行。两边要求相反。
- **执行策略**：默认 `Restricted` 跑不了 .ps1，所以 .bat 里必须带
  `-ExecutionPolicy Bypass`。
- **卸载脚本不能因为一项删不掉就整体中断**。实测被安全软件拦住单个文件时，
  `$ErrorActionPreference = "Stop"` 会让整个卸载停在半路。改成每项 try/catch，
  最后汇总提示。
- **删自己的目录要分两步**：先把除脚本外的内容删光，再交给后台 cmd 删空目录。
  只做后者的话，后台进程一旦没起来，用户就剩 120MB 垃圾。
- **UserChoice 会压过注册表关联**。这台机器 .pdf 被 WPS 占着
  （UserChoice = SW.PDF.Document），装了也不会生效。安装脚本会检测并提示
  去"设置→默认应用"改，这是 Windows 10/11 的机制，绕不过。

### 实测记录

- 安装：87 个文件 / 121MB / 快捷方式×2 / `.pdf`→PDFStudio.Document /
  卸载项登记 / 原关联 SW.PDF.Document 已备份
- 已安装的 exe 自检：`SELFTEST OK ... 打印链路正常`
- 卸载：目录、快捷方式、ProgId、备份键、卸载项全部清空，`.pdf` 还原为

- zip 解压后直接跑 exe：通过

### 教训

25. 打包类任务里，"文件存在"不等于"功能可用"。打印、字体、图标这类
    要靠**真的执行一次**才算验证过，所以自检里必须包含打印链路。
26. 用户说"要关联 PDF"时，得先想到 UserChoice 这个机制，否则装完不生效

## 收尾：.bat 换行 bug + 安装脚本两个真 bug

### 用户报的现象

```
'etlocal' 不是内部或外部命令
'ho.' 不是内部或外部命令
''
找不到 PDFStudio.exe。
```

### 根因

`安装.bat` 存成了 **LF 换行**。cmd 读批处理是按字节偏移解析的，
少了 `\r` 之后解析位置整体错位：`setlocal` 被读成 `etlocal`，
`echo.` 读成 `ho.`，`cd /d "%~dp0"` 也没生效，
所以后面的 `install.ps1` 在错误的目录里跑 → 找不到 PDFStudio。

修法：`packaging/windows/_fix_scripts.py`，规则两条方向相反——
`.bat` = CRLF + 无 BOM，`.ps1` = CRLF + UTF-8 BOM。
并且 `make_zip.py` 打包前**自动调用**它，不依赖"记得手动跑"。

### 顺手查出并修掉的两个真 bug

1. **重复安装会把关联备份覆盖成自己的 ProgId**
   第二次安装时 `.pdf` 已经是 `PDFStudio.Document`，备份被改成同样的值，
   卸载就把 `.pdf` 还原成一个刚被删掉的 ProgId → 双击 PDF 变成"没有关联"。
   现在只在 `.pdf` 不是自己时才写备份。

2. **`New-Item -Path <注册表键> -Force` 会重建整个键**
   实测：往 `HKCU:\Software\__probe` 写默认值 + 子键，再 `New-Item -Force`，
   默认值变空、子键全没了。原脚本用它建 `.pdf` 键，
   等于把系统放的 `OpenWithProgids` / `PersistentHandler` 一起清掉，
   用户以后"用别的程序打开"里就找不到原来的阅读器了。
   一律改成先 `Test-Path` 再建。

这次 `etlocal` 那几行没了，说明换行修好了；剩下的是找不到程序目录。

### 不再猜，改成让脚本把现场打出来

`install.ps1` 找不到 `PDFStudio.exe` 时，现在会打印：
脚本所在目录、该目录里的完整清单（标出文件/文件夹）、
以及按情况判断的原因（没有 PDFStudio 文件夹 → 大概率是在压缩包里双击了；
有文件夹但没 exe → 大概率是杀软隔离）。另外支持 `-AppDir <路径>` 手动指定。

同时 `Find-AppSource()` 兜住四种布局：
标准 `PDFStudio\`、多套一层、子目录直接摊开、**源码目录的 `dist3/PDFStudio`**。
最后这个是关键——开发机上双击 `packaging/windows/安装.bat` 时，
程序在 `dist3` 下，不认它就一直报"找不到 PDFStudio.exe"，看起来像打包坏了。
我自己第一次跑测试就是踩的这个坑。

### 又抓出三个真问题

1. **`.bat` 的 `rem` 行不能写中文**
   `chcp 65001` 下 cmd 解析含中文的 `rem` 行会错位，把后半句当命令执行：
   `'文的参数错误，用户看不懂。' is not recognized as an internal or external command`
   中文放在 `echo` 里完全正常，只有 `rem` 会中招。已把所有 `rem` 改成英文，
   并加了静态检查 `bad_rem_lines()`。

2. **`pause` 把 ERRORLEVEL 冲成 0**
   安装失败也返回 0，任何包装脚本都会以为成功。改成
   `set "RC=%ERRORLEVEL%"` → `pause` → `exit /b %RC%`。

3. **只解压出 `.bat` 时甩给用户一串英文 PowerShell 报错**
   加前置检查：`if not exist install.ps1` → 中文提示"直接在压缩包里双击了本文件"。

### 测试补的场景（40 → 44 项）

- 多套一层目录 → 自动找到
- 源码目录 `dist3/PDFStudio` → 自动找到，并提示"这是开发构建目录"

### 教训

31. **`chcp 65001` 的 .bat 里，中文只能出现在 `echo` 后面**。`rem` 行含中文
    会被截断成半句当命令执行，而且这个错误长得很像"文件损坏"，很难联想。
32. **`pause` 会覆盖退出码**。想让脚本能报告失败，必须在 `pause` 之前存 ERRORLEVEL。
33. **断言查错误要中英双语**。`chcp 65001` 之后系统消息变英文，
    只查「不是内部或外部命令」等于没查——那一轮 42 项全绿，
    实际输出里明晃晃有一行 `is not recognized`。
34. **工具报"找不到 X"时，先让它把"它看到了什么"打印出来**。
    否则用户只能描述现象，我只能列可能性，来回猜。
