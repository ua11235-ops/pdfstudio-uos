## 发现并修掉：UOS 发行包比源码旧了三天，功能整个缺失

### 现象

`packaging/build/pdfstudio-1.0.0.tar.gz`（79.8MB）是 **10-28 19:54** 打的，
而「合并 PDF 文件」功能是 **10-29 / 10-30** 加的。比对包内与工作区，4 个文件不同步，
并且：

- 包里**没有** `pdfstudio/core/merge.py`、`pdfstudio/ui/merge_dialog.py`
- 包里的 `main_window.py` 不 import MergeDialog，也没有 `Ctrl+M` / 「合并 PDF 文件…」
- 包里的 README 还是 283 行的旧版（没有「合并多个 PDF」整节）

更要命的是这个包**能解压、能安装、能启动**——只是少了一整个功能。
用户拿到手只会觉得"说好的合并呢"，而开发机上测试全绿。

### 根因

`make_release.sh` 是 shell 脚本，而这台开发机没有 bash。于是"重新打包"这件事
在开发机上根本执行不了，只能靠人记得去别的机器上跑。记忆里其实已经记过这条教训
（10-28「发行包变小」那次），但当时的结论是"重打时别忘加 `--with-wheels`"，
没有触及"这个脚本本机跑不起来"。

### 改法

1. 新增 `packaging/make_release.py`：打包逻辑用 Python 重写，全平台可跑。
   `make_release.sh` 改成转发壳（`exec python3 make_release.py "$@"`），
   两个入口永远打同一个包，不会各打各的。
2. **默认自检**：打完后核对包内容——`REQUIRED` 里 29 个必需文件缺一个就报错；
   `packaging/windows/dist*` / `build*` 泄漏就报错；`__pycache__`/`.pyc` 泄漏就报错。
   `--no-verify` 才能关。这一步不做成"记得加的开关"，因为出事的正是没人核。
3. 排除规则按**路径段**判断而不是字符串前缀（`./sample` 前缀会误伤 `./samples`）；
   PyInstaller 产物按 `dist`/`build` 前缀匹配，下次换 `dist9` 也自动排除。
   顺带修掉一个隐患：按旧脚本的排除表，本机重打会把 101MB `dist8` + 43MB
   `build` + 11MB `build8` 全塞进去，包会从 79MB 变成 236MB。
4. tar 里显式写 `mode=755`（`run.py` 和 `packaging/*.sh`）、uid/gid 归零。
   源码在 Windows 上维护没有 Unix 执行位，不写的话 UOS 上解包后
   `sudo ./packaging/install.sh` 会 Permission denied。
5. `smoke_core.py` 加第 39 项「发行包收集规则」，**破坏性验证过三次**：
   - 不排 `dist/build` → `构建残留混进发行包：[...]` ✓
   - `collect()` 跳过 merge 模块（等价于 10-28 那个包）→
     `发行包会缺文件：['pdfstudio/core/merge.py', 'pdfstudio/ui/merge_dialog.py']` ✓
   - `--with-wheels` 收不到 wheel → `有 wheels 目录却只收到 0 个` ✓
   - 还原后 39 项全绿 ✓

   第一次写这条测试时自己踩了坑：用 `collect(True)` 拿到结果又断言"不该有 wheel"，
   直接自相矛盾报错；改完再测。另外**破坏点必须打在 `collect`/`should_skip` 上**，
   删 `REQUIRED` 里的需求项等于把断言删掉，测试照样绿（第一版就这么白验了一轮）。

### 教训（接 34 条往下）

35. **"重新打包"如果不能在本机一条命令跑完，它就一定会烂掉**。这次包停在
    源码前三天，功能整个缺失，而所有测试都是绿的——因为测试测的是源码，
    不是交付物。构建脚本本身要能在开发机上跑，并且要有牙。
36. **打包脚本的排除表要按路径段写，不能按字符串前缀**。`./build` 这种前缀
    既会漏（`./packaging/build`）也会误伤（`./sample` vs `./samples`）。
    `dist8`、`build8` 这种带序号的目录名更不能写死，下次失败重试就换号了。
37. **"文件都在"不等于"包是对的"**。核对要分两个方向：缺了什么（`REQUIRED`）
    和多了什么（构建残留）。只查一边的话，包能解压、能启动、少个功能，
    照样交付出去。
38. **写断言时别把被测数据当成被测行为**。这次第一版测试用 `collect(True)`
    的结果去断言"不该有 wheel"，逻辑自相矛盾；破坏性验证时又删掉需求项去
    "制造 bug"，等价于删断言。破坏点必须打在被测函数上。
