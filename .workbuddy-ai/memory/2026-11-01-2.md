## 修「合并拖拽还是没能成功」（用户第二次报）

### 前两轮为什么都白修了

10-29 和 10-30 各修过一次拖拽，都是在 `dragEnterEvent`/`dropEvent` 里动刀
（mime 判定、CopyAction、落点线），测试也补了，全绿。但用户还是拖不动。

这次先做实验再动手，才发现方向从一开始就错了：

- 探针 1（子类覆盖 `startDrag`）证明 **拖拽确实开始了**——
  `startDrag` 被调用，说明"没触发拖拽"的假设是错的
- 探针 2（真实 `QDrag::exec`）证明 **exec 进去就出不来**：
  松手后没有任何响应，进程停在模态循环里
- 探针 3（在模态循环内部用 QTimer 投递鼠标事件）同样出不来

原来 `QDrag::exec()` 是**平台级模态循环**，本机上它根本走不完。
前两轮改的 `dragMoveEvent`/`dropEvent` 全部运行在这个循环**内部**——
循环都出不来，改里面的代码当然没用。

### 更深的教训：测试测的是 QDrag 之外的那一半

旧测试为什么全绿？因为它断言的是：

```python
assert lst.dragEnabled()                                    # 配置对不对
assert lst.dragDropMode() != NoDragDrop                     # 配置对不对
assert enter.isAccepted()                                   # 事件接受吗
```

这些全是"配置"和"exec 之外"的东西。而真正的故障在 exec 内部，
**测试根本进不去那个模态循环，所以永远测不到**。这不是测试写得糙，
是选错了被测层面。

### 改法

`MergePageList` 完全不用 Qt 内置拖拽：

- `setDragEnabled(False)` + `setDragDropMode(NoDragDrop)`（保留 `setAcceptDrops(True)`，
  外部拖 PDF 进来是另一套事件）
- `mousePressEvent` 记起点和抓到的页
- `mouseMoveEvent` 超过 `startDragDistance()` 才进拖拽态（否则单击就搬页 = 误操作）
- `mouseReleaseEvent` 调 `apply_drop()`
- 拖回原地时通过 `dragFinished` 信号让标题栏提示「顺序没有变化」，
  免得用户把"没搬动"当成"坏了"

没有模态循环、没有平台差异，**测试可以用 QTest 发真实鼠标事件跑通全程**。

### 测试换成真鼠标

删掉 `t_merge_internal_drag_events`（测配置的那个），换成
`t_merge_real_mouse_drag`：QTest 按下 → 分 6 步移动 → 松手，断言

1. 往后拖页序真的变、模型跟着变、选中落在正确位置
2. 往前拖也变
3. 拖回原地顺序不变（且不卡死）
4. **单纯单击不搬行**（防误操作）
5. 拖完 `_drag_start`/`_dragging`/`_drop_row` 全部复位

**破坏性验证**：把拖拽退回 Qt 内置实现（等价于修复前），`ui_smoke.py`
直接**挂死**（90 秒超时）。这本身就是最有力的证据——挂死就是用户遇到的
"拖不动"。还原后 26 项全绿。

> 破坏验证的子进程**必须带 timeout**：这次"变红"的表现是挂死而不是断言失败，
> 没有超时就会卡住整轮验证。

### 教训（接 38 条往下）

39. **同一个功能修两次还没好，就不要再改同一个地方了，先去做实验**。
    前两轮都在 `dragEnterEvent`/`dropEvent` 里找问题，而真正的故障是
    `QDrag::exec` 这个模态循环根本走不完——改循环里面的代码毫无意义。
    一个 20 行的探针脚本顶两轮盲改。
40. **测试只能证明它所在层面的东西**。断言 `dragEnabled()` 为真、
    断言事件被接受，都是"配置层"；而故障在"事件循环层"。
    测不到的东西要换实现方式让它变得可测，而不是加更多配置断言。
41. **"测试挂死"是有效信号**。破坏性验证时脚本挂死不要立刻当成工具坏了，
    先想"挂死的位置是不是就是故障位置"。这次挂死正是 `QDrag::exec`。
    但破坏验证必须给子进程设 timeout，否则自己也跟着挂。
42. **平台级模态循环（`exec()` 系列）是自动化测试的天敌**。
    遇到"逻辑都对但用户说没反应"的 GUI 问题，先确认这条链路上有没有
    `exec()`；能用事件处理自己实现的，就别交给框架的模态循环。
43. **环境本身跑不起来时，"测试通过"是假的**。这次工作区里连
    `python.exe` 都起不来，如果在里面跑测试并看到"通过"，那个通过毫无意义
    （实际是根本没执行）。换环境前后都要确认进程真的起来了。
