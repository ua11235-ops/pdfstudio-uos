## 修「缩略图上拖动事件和框选事件重复」

### 现象与根因

用户反馈：拖缩略图时，拖动排序和框选同时在发生。

根因在 `ThumbnailList.mouseMoveEvent` 的早期分支：

```python
if not self._dragging:
    if moved < startDragDistance():
        QListWidget.mouseMoveEvent(self, event)   # ← 转发给基类
        return
```

在"还没越过拖拽阈值"那一段，事件被无条件转发给了基类。基类收到按住+移动
就开始橡皮筋框选；而一旦越过阈值，我们又把它当拖页处理、开始算落点。
于是**同一段拖动里，框在画、页序也在动**——正是用户说的"重复"。

### 改法

1. **按按下位置决定手势，且只判一次**（越过阈值那一刻）：
   按在条目上 → `_DRAG_PAGE`；按在空白处 → `_DRAG_BAND`
2. **阈值内什么都不做**，不再转发基类。基类拿不到移动事件，就不会自己开框
3. **框选也自己实现**：`_band_extent()` 算矩形、`_apply_band_selection()`
   按矩形相交重算选中、`_paint_band()` 画半透明框
4. 拖页分支 `event.accept()` 吃掉事件，基类彻底碰不到

### 为什么框选也要自己写（关键发现）

先做了**基线测试**：一个裸 `QListWidget`（不拦截任何事件），用 QTest 发
按下 + 拖动，IconMode 和 ListMode **都选不中任何条目**。

也就是说基类的橡皮筋框选在自动化测试里根本无法验证。如果继续依赖它，
"框选好不好用"永远只能靠人点——而这个项目已经吃过两次
"测试全绿但用户用不了"的亏。自己实现后，框选有了可断言的中间状态
（`_band_rect`）和可验证的结果（选中集合）。

### 测试

`ui_smoke.py` 第 28 项「缩略图拖拽与框选互不干扰」，逐帧断言：

- 按在条目上拖：`_drag_mode == _DRAG_PAGE`，全程 `_band_rect is None`，
  松手后页序真的变
- 按在空白处拖：`_drag_mode == _DRAG_BAND`，全程 `_drop_row is None`，
  页序一页都不许动，框中确实选中了页面，松手后 `_band_rect` 清掉

### 破坏性验证

1. 不区分手势（空白处也当拖页）→
   `AssertionError('空白处拖动应判为框选，实际 1')` ✓
2. 拖页时也把事件转给基类 →
   被「拖拽能直接改页序」抓住：`['P-2','P-3','P-4','P-5','P-1',...]`
   （基类重复处理导致多搬一次）✓
3. 还原后 28 项全绿 ✓

### 教训（接 45 条往下）

45. **两份逻辑同时消费同一个事件流，症状是"重复"**。修这类问题不能靠
    "加个判断让它不生效"，要让**同一时刻只有一条路径活着**：
    判定一次、之后分支互斥、该 `accept()` 的就吃掉事件。
46. **转发给基类是有代价的**。`super().mouseMoveEvent()` 不是"顺手更新一下
    内部状态"，它可能启动一套完整的手势（这里是橡皮筋框选）。
    自己接管手势时，阈值内宁可什么都不做，也别转发。
47. **改之前先测基线**。这次要是没先测"裸 QListWidget 的框选在 QTest 下
    根本选不中"，就会一直以为是自己的拦截逻辑写错了，白改几轮。
    基线测试只花 20 行，省下的是反复猜。
48. 破坏性验证的判定要**放宽到整套测试**：这次破坏 2 是被邻近用例抓住的，
    只盯新加的那条会误判成"没抓到"。但"还原后必须变绿"这条不能放宽。
